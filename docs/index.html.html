Which pages actually need a content refresh? A client-generalizable scoring model

Rupam More — FlyRank ML Internship Capstone — Refresh / Content Opportunity Scoring

Abstract. Content teams can't manually review every page for decline, and simple rules (like "flag anything past position 10") barely beat chance. This project asks whether a model trained on 90-day search performance windows can identify pages likely to keep declining, using features that exist before the decline happens. A Random Forest trained on impression trends, ranking position, position volatility, and query-mix signals from FlyRank's search warehouse reached 0.905 ROC-AUC on pages from clients never seen during training, against a 0.560 baseline for the position-only rule. The result is a ranked action queue: about a third of scored pages get a concrete recommendation (rewrite, review, or watch), the rest get left alone — which is the actual point of scoring at all.

Introduction

Content teams generally can't review every page on a regular cadence — there are too many, and most don't need attention. The decision this project supports is: which pages should a content team look at first, and why, so review time goes to pages that are actually declining rather than pages that just look busy.

A wrong call here has a real cost either direction. Flagging a stable page wastes review time. Missing a genuinely declining high-traffic page means it keeps losing visibility for another review cycle. The scoring model exists to make that trade-off better than a fixed threshold does.

Data

This project uses FlyRank's internship warehouse release: ~17 months of daily search performance across roughly 70 pseudonymized clients, plus a query-level table describing how each page earns its impressions. All identifiers are pseudonymized content and client hashes — no client names, domains, or raw queries appear anywhere in this analysis.

Two 90-day windows were used per page: a feature window and, immediately after it, an outcome window used only to define the label — never to build a feature. Pages with fewer than 100 impressions in the earlier window were excluded to avoid scoring on noise.

Methodology

Task framing: binary classification — will this page's impressions decline by more than 20% from one 90-day window to the next.

Features (all computed from the feature window only, before the outcome window exists):

  • Prior-window impressions
  • Average search ranking position
  • Position volatility (standard deviation of position over the window)
  • Share of impressions from rare/long-tail queries
  • Share of impressions that are anonymized (below reporting threshold)
  • Concentration of impressions in the page's single top query

Leakage check: every feature is built strictly from data available before the outcome window begins, so the model cannot see the answer while learning the question.

Validation: pages were split by client, not at random — training and test sets never share a client. A random split would let the model partly memorize a client's baseline behavior rather than learn a pattern that generalizes to pages it has never seen from clients it has never seen. This is a harder, more honest test than it first appears, and the gap between a naive split and this one is itself worth reporting for any future work on this dataset.

The baseline's 0.560 is close to a coin flip — a single position threshold captures almost no signal about which specific pages are trending down. The model's 0.905 on unseen clients indicates the decline pattern is learnable from window-over-window behavior, not just tied to how any one client's pages happen to behave.

Turning scores into an action queue and reviewing the distribution (not just the raw probability count) mattered here: an early, uncalibrated volatility cutoff flagged 87% of all pages for some action, which defeats the purpose of prioritizing. Comparing that cutoff against the actual distribution of position volatility (median 10.9, well above the initial guess of 5) and recalibrating it to the 90th percentile brought the flagged share down to a workable 36.6%:

Limitations & Honest Framing

  • This model identifies pages statistically likely to keep declining — it does not prove why any individual page is declining, and it makes no claim about Google's ranking algorithm.
  • "Decline" here means a 20% impression drop between two fixed 90-day windows. A page with a real but slower decline, or one that dips then recovers mid-window, may not trip this specific definition.
  • The client-held-out split is a stronger test than random splitting, but 0.905 should still be read as this dataset's result, not a guaranteed number on a different search population.
  • The action-tier thresholds (0.65 probability, 1,000 impressions, 90th-percentile volatility) are calibrated to this dataset's distributions. They should be re-checked, not copy-pasted, on new data.
  • Results are decision-support for a human content team, not an automated publishing action — see the recommendations below.

Ranked Recommendations

  1. Route P1 (Rewrite/Refresh) pages to the content team first — these combine high decline probability with meaningful existing traffic, so they carry the largest cost if left alone.
  2. Treat P2 (Content Review) as a lighter-touch queue — same decline signal, lower stakes per page, suitable for a faster review pass.
  3. Don't action P3 (volatile) pages immediately — volatility alone isn't decline. Re-check them next cycle to see if the swing resolves on its own.
  4. Re-run the volatility and probability thresholds against each new data pull rather than reusing fixed numbers — this project's own first pass shows how much a wrong threshold changes the result.
